## 〇、阅读前提

### 被测对象

cxx_ci 是两个互不 import 的项目，只靠文件与命令行协作（契约登记在 `CONTRACT.md`）：

| 项目 | 运行环境 | 第三方依赖 | 职责 |
| --- | --- | --- | --- |
| `ci/` | Python ≥ 3.4 | 无（标准库） | 阶段编排与门禁：`boundary` / `clean` / `build` / `build_test` / `run_test` / `memcheck` |
| `standardize/` | Python ≥ 3.11 | `PyYAML`；可选 clang 二进制包 | 排版、风格（clang-tidy）、命名 |

生产代码 43 个文件、17477 行（不含测试与 vendored 目录）。

### 本轮用到的三个机制（后文反复出现）

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| 配置审计 | `ci/lib/audit.py`、`standardize/.../audit.py` | 只读比对配置与源码，抓三种漂移：死配置（写了没人用）、配置旁路（源码里写死了与配置取值相同的字面量）、编译标准未锁定 |
| 范围归因 | `ci/lib/paths.py:62 scope_of` | 把任意路径判成 `project` / `excluded` / `external`，决定诊断是否计入门禁 |
| 基线清单 | `ci/lib/xfail.py`、`standardize/.../xfail.py` | 存量问题登记后不算失败；**登记条目若不再命中要反向报"清单过期"** |

### 测量方法（可复现）

1. **精确重复块**：去注释、去空行、折叠空白，取连续 6 行做哈希种子，命中即向两边扩展直到某一行不同，
   只报 ≥12 行、且出现在 ≥2 处（或同文件 ≥2 处）的块，重叠位置只计一次。
2. **函数级近似重复**：按 AST 取函数体，行数 ≥18，先比函数体内标识符集合的 Jaccard ≥0.5，
   再用序列相似度 ≥0.82 定性；跳过同文件相邻函数。
3. **整文件相似度**：同法归一化后做序列相似度，>0.45 才列出。

### 基线（本文的改进都以此为对照）

| 指标 | 实测 | 评价 |
| --- | --- | --- |
| ≥12 行逐字重复块（生产代码） | **3 组，冗余约 38 行**（占 17477 行的 0.2%） | 很好 |
| ≥12 行逐字重复块（测试代码 30 个文件） | **0 组** | 很好 |
| 函数级近似重复（测试代码） | **0 对** | 很好 |
| 函数长度 | 481 个函数，>60 行 9 个，>100 行 2 个 | 健康 |
| 最大模块 | 827 行 / 29 个顶层函数 | 无上帝模块 |
| 子进程调用 | 裸 `subprocess` 仅 10 处，其余统一走 `ci/lib/tools.py` / `standardize` 侧封装 | 一致 |
| 整文件相似度 | 仅 1 对 >0.45：`ci/lib/audit.py` ↔ `standardize/.../audit.py` = **0.702** | 见 F3 |

**总体判断：这个仓库的重复度低于同类工具，问题不在"到处复制"，而在三处该收口的地方没收口——
其中一处已经造成行为不一致，一处已经造成规则漂移。** 下面按"是否会出错"排序。

## 一、F1【P1】"路径是否在某目录内"有 4 种写法，判定口径会相反

### 缺陷点

同一个谓词（路径 `p` 是否位于 `root` 之内，含边界判断）在 cxx_ci 里有 4 份实现，且**归一化方式两两不同**：

| # | 位置 | 归一化 | 是否解软链接 |
| --- | --- | --- | --- |
| 1 | `ci/lib/paths.py:32 is_within` | `os.path.realpath` | **解** |
| 2 | `ci/lib/paths.py:62 scope_of`（同一文件内另写一遍前缀比较） | `os.path.abspath` | 不解 |
| 3 | `ci/lib/diagnostics.py:33 _inside` | `normpath(abspath(...))` | 不解 |
| 4 | `standardize/.../style.py:86 _inside` | `normpath(abspath(...))` | 不解 |

`scope_of` 是范围归因的唯一入口（诊断展示、`style`/`format` 的处理范围、内存检查归因都调它），
而它内部用的是**不解软链**的前缀比较；`clean` 与 `boundary` 走的是**解软链**的 `is_within`
（`ci/stages/clean.py:49`、`ci/lib/boundary.py:135,148`），`valgrind` 归因走 `is_within`
（`ci/lib/valgrind.py:275`），诊断归因走 `_inside`（`ci/lib/diagnostics.py:74,81`）。

**后果不是风格问题，是判定相反**：当 `BUILD_DIR` 或项目根经过软链接（共享目录、`/home` 挂到别处、
`ccache`/`distcc` 常用布局、把第三方库软链进工程）时，同一个文件会出现——

- `clean` 认为它在构建树"之外"（realpath 后不再是 `BUILD_DIR` 的后代）→ 拒绝清理，报"越界"；
- `diagnostics` 认为它"在项目内"（abspath 后仍是）→ 把第三方头文件引发的诊断算作项目自身问题判红；
- 反过来也成立：软链进来的第三方目录被 `scope_of` 判成 `project`，被 `is_within` 判成 `excluded`。

也就是说**同一条诊断在 `run_test` 阶段计入、在 `memcheck` 阶段不计入**，用户看到的是"两个阶段对同一份
代码给出不同结论"，且没有任何一处提示是路径解析差异所致。这类问题的排查成本极高，因为每一处单独看都"对"。

另外，`scope_of` 与 `is_within` 对"路径恰好等于 root"的处理也不一致（前者等于 root 算 `project`；
后者有 `strict` 参数才排除），这类细节差异靠人记是记不住的。

### 改进后的预期效果

- 全仓库只有**一个**"路径包含"谓词，归一化策略写在它的 docstring 里，并由一条测试钉住；
  其余三处变成对它的调用。
- 对软链接的取舍变成显式决定：默认**解软链**（与文件系统真实行为一致），并把"解链后是否仍在项目内"
  作为唯一口径；如果某处确实需要不解链的比较（例如比较两个尚未创建的路径），改为调用同一大函数的
  具名变体（`is_within_logical`），调用点写明为什么用逻辑比较。
- 同一条诊断在编译、测试、内存检查三个阶段归因一致；构造一个软链构建目录的回归测试，断言同一文件
  在三处归因相同。
- `clean` 的越界保护与范围归因共用同一实现，杜绝"能删的判成不能删、能改的判成不能改"。

### 改进方案

1. `ci/lib/paths.py` 保留唯一实现，两个具名入口：
   `is_within(path, root, strict=False)`（`realpath`，用于一切与真实文件系统相关的判断）与
   `is_within_logical(...)`（`abspath`，仅用于路径还不存在、不能碰文件系统的场合）；
   删除 `diagnostics._inside` 与 `style._inside`，改调 `paths`（standardize 侧不能 import `ci`，
   在 `standardize/.../paths.py` 建**同名同实现**的副本，并由 F3 的同固件测试保证两者不漂）。
2. `scope_of` 内部改为调用 `is_within`，自己只保留"排除区优先于项目区"的三态语义；
   `strict` 语义收敛成"等于 root 本身算不算在内"一个参数，两处一致。
3. 归一化时机收口：**只在入口归一化一次**（读入配置时把 `ROOT` / `BUILD_DIR` / `SCOPE` 各项解析成
   realpath），后续比较一律用已归一化的值，避免同一函数里 `abspath` 与 `realpath` 混用。
4. 回归测试（两侧各一份）：`BUILD_DIR` 是指向工程外目录的软链、工程根本身是软链、第三方目录被软链进
   工程三种布局下，断言同一文件的归因结果在 `clean` / `diagnostics` / `valgrind` / `style` 四处一致。
5. 自检：把"禁止自行做前缀比较"变成可机检纪律——在 `audit.py` 的"配置旁路"检查旁边加一条源码级检查，
   拦 `ci`/`standardize` 自身源码里新的 `startswith(` + `os.sep` 组合（`paths.py` 白名单除外）。

## 二、F2【P1】`style` 的三个入口把前置准备各写一遍，且已经漂移

### 缺陷点

`standardize` 的 `style` 有三个入口：`check`（`style.py:241`，104 行）、`record`（`:420`，47 行）、
`apply`（`:477`，64 行）。它们各自内联了同一段前置准备：

```
collect_files → 空集早退 → ensure_database_with_build → 校验 .clang-tidy 存在 → （取增量改动集）
```

`style.py:266-282` 与 `:484-498` 有 **13 行逐字相同**；`ensure_database_with_build` 与紧随其后的配置存在性
检查在 `:266`、`:430`、`:484` 出现**三遍**。全仓最大的两个函数（`_apply_files` 140 行、`check` 104 行）
正是这种内联的产物。

**已经漂移的证据（不是推测，是调用点清点）**——`style.prepare()`（`:99`，生成 `moc_`/`ui_`/`qrc_` 派生文件，
其 docstring 明确写着"缺了它们，含 `#include "X.moc"` 的翻译单元会被判成编译错误，该 TU 的 fix-it 也一并
被抑制——不是分析结果差一点，而是完全不可用"）只在 `check` 里被调用（调用点唯一：`style.py:248`），
`record` 与 `apply` **都不调用它**。`--no-prepare`（`cli.py:83`）也只对 `check` 生效。

对照同项目的 `format`：它的 `prepare` 在 `format.py:134`（check）与 `:214`（apply）**两个入口都调**。
同一项目里两个模块对"分析前必须准备派生文件"这条规则的执行方式不同，就是复制前置代码的必然结果。

触发条件（不是必然触发，因此更难发现）：编译数据库已存在但构建树里没有派生文件时——
`DB_PROVIDER` 用 cmake 只做配置未真正编译、`bear` 之外手工放入 `compile_commands.json`、
`clean` 之后只重新配置。此时：

- `style --record`（接入时的推荐第一步，用来"存量冻结成基线"）会**漏登记**这些 TU 的诊断；
  随后 `style`（会 prepare）把它们报成**新增违规**——用户没改代码，门禁却红了，且指向的文件正是
  Qt 工程里最需要检查的那些（含 `Q_OBJECT` 的类）。
- `style --apply` 对这些 TU 一条都改不动，但因为"改不动"在本工具里是正常状态，退出码可以仍然是 0。

### 改进后的预期效果

- 三个入口的前置准备只有一份代码；新增第四个入口（例如将来的 `explain`）不可能漏步骤。
- "分析前必须生成派生文件"变成入口无关的硬约束：`--record` 与 `--apply` 与 `--check` 看到的待分析集合
  完全一致（同一时刻、同一配置下三者的诊断条数可比）。
- 派生文件生成失败时，三个入口的行为一致：走 stderr、并且**结果不完整这一事实被记录进结论**，
  不允许 `--apply` 在"实际什么都没修"的情况下静默返回成功。
- `check` 与 `_apply_files` 的长度降到 60 行以内，读一个入口不用再读三遍样板。

### 改进方案

1. 抽一个共享前置，签名大致
   `_prepare_run(config, options, tools, *, need_database=True, need_checklist=True, apply_incremental=True)`，
   返回携带 `files / database_dir / config_file / checklist` 的小结构（失败时返回错误码与说明）；
   三个入口只保留自己的判定与写回逻辑。
2. 把 `prepare` 调用移进 `_prepare_run`（受 `config.tidy_prepare` 与 `--no-prepare` 控制，语义不变），
   使三个入口一致；`record` 不做增量收窄这件事（登记基线本就该全量）**在 `_prepare_run` 里写成显式
   关键字参数 `apply_incremental=False` 并加一行注释**，把"有意的差异"和"漏了"区分开。
3. 派生文件准备失败时：`check` 维持现状（stderr + 继续），`apply` 与 `record` 改为在结论行加
   "派生文件未就绪，结果不完整"并在 `--strict` 下判失败；不允许"0 个 TU 被分析"与"全部 TU 干净"
   给出相同输出（这条与既有原则"未跑≠干净、跳过≠通过"是同一条纪律）。
4. 顺手（只在动这些函数时做，不单独开改动）：把 `_apply_files`（140 行）按"改前快照 / 应用 fix-it /
   复扫验证 / 回滚"四步拆开，每步一个函数。
5. 测试：①三入口对同一 fixture 产生相同的诊断集合（消除 F2 的漂移）；②"有 DB 无派生文件"场景下
   `--record` 会先生成派生文件（断言 `moc_*` 被调用）；③前置步骤只被调用一次（用计数断言防回潮）。

## 三、F3【P1】两份 `audit.py` 是同一功能的两遍实现，且没有防漂移机制

### 缺陷点

| 项 | `ci/lib/audit.py` | `standardize/.../audit.py` |
| --- | --- | --- |
| 行数 / 顶层函数 | 598 行 / 34 个 | 504 行 / 32 个 |
| 整文件相似度 | **0.702** | 全仓唯一 >0.45 的文件对 |
| 函数名重合 | **31 个同名**（`_parse_all`、`_referenced_names`、`_check_bypass`、`_check_dead`、`_check_std`、`string_literals`、`_value_owners`…） | 同左 |
| 各自独有 | `_expand_glob`、`_glob_regex`、`_qmake_project`（3.4 的 glob 不认 `**`） | `_check_header_filter` |
| 逐字重复 | `:184-195`（12 行）、`:242-254`（13 行） | 对应 `:120-131`、`:166-178`；`_referenced_names` 相似度 0.979 |
| 文档 | 模块 docstring 的三条判据近乎逐字相同 | 同左，只有"构建文件里锁哪个变量"一句不同 |

需要说清楚的是：**分叉是有正当理由的**。`ci` 侧必须跑在 Python 3.4 上，`audit.py:100` 与 `:215` 两处注释
分别记录了被迫的差异（3.4 的 `glob` 不支持递归 `**`；3.4 把字符串与字节分成两种 AST 节点，3.6 起统一成
`Constant`）。而两个项目"互不 import、只靠文件与命令行契约协作"是写在设计里的约束。
所以**这里不该被简单判成"该合并没合并"**。

真正的问题是：约 1100 行、占全部生产代码约 6% 的同一套规则存在两份实现，**而两侧各自只有自己的测试**
（`ci/tests/unit/test_audit_config.py`、`standardize/tests/test_audit.py`），没有任何机制保证同一份代码
在两侧审计出同样的结论。三种漂移已经可以预期：

- 改一条判据（例如"文档字符串不计入旁路"这条豁免）只改一侧，另一侧静默保持旧行为；
- `ci` 侧因为 3.4 语法限制长期落后，两侧规则集合会随时间分叉（`_qmake_project` 那类是必要差异，
  但必要差异与遗漏差异看起来一模一样）；
- 修 bug 时最容易只修读代码时手边那一份——`_referenced_names` 这种 0.979 相似的函数正是高发区。

同一现象的小一号版本：`ci/lib/xfail.py:189 verdict` ↔ `standardize/.../xfail.py:250 verdict`，
相似度 0.836，都在实现"登记的条目若不再命中要反向报清单过期"这一条规则，也没有交叉验证。

### 改进后的预期效果

- 两侧的审计/清单规则**同漂移即测试红**：喂同一份 fixture（同一份源码 + 同一份配置）给两侧，
  断言输出集合一致；必要的语言版本差异用显式豁免表声明，而不是靠人记。
- 新增一条审计判据时，作者被迫同时提供 fixture；豁免表里每一项都要写"为什么豁免"，半年后能审。
- 阅读者能一眼看出"这两份是刻意的平行实现"：两侧文件头各有一行指向对方与对照测试的位置说明。
- 不再出现"同一份代码在 `ci` 侧审不出、在 `standardize` 侧审出"的答疑。

### 改进方案

1. **不引入第三个共享包**（那会破坏"两个项目互不 import"的架构约定，收益不足以支付这个代价，见 §六）。
   改为**同固件对照测试**：新增 `tools/parity/audit_fixture/`（一份小工程：含 `.pro`、`CMakeLists.txt`、
   几个 `.cpp/.h`、一份配置），两侧测试各自跑自己的 audit，把结果规一化成
   `(判据, 相对路径, 配置键)` 三元集合，断言两个集合相等。豁免表写成 `tools/parity/exemptions.json`，
   每条形如 `{"rule": "std_pin", "side": "ci", "why": "3.4 无 ** glob"}`。
2. 明确"参照实现"：`standardize` 侧是参照（现代 Python、能跑全部判据），`ci` 侧是兼容移植；
   两侧文件头各写一行"与 <对方路径> 为平行实现，改动须同步并跑 `tools/parity` 对照"。
3. 把可移植的公共部分**在两侧内部各自收口**，减少平行面积：例如 AST 字面量收集、`_read_lines`、
   `_parse_all`、`_referenced_names` 在每侧内部都只留一份，任何新功能不得再复制一份——这样平行实现的
   面积只减不增，而不是继续长出第三份。
4. `xfail` 的 `verdict` 规则同样加同固件对照测试（同一份清单 + 同一份实际命中集合 → 断言两侧的
   "已修复/仍存在/新增"三态分类相同）。
5. 若将来确需抽共享模块，前置条件是：先把它登记为 `CONTRACT.md` 的契约项、明确它属于哪个 Python 版本
   下限、并说明"两个项目仍能各自独立部署"如何维持——不满足就不做。

## 四、F4【P2】重复度没有度量，也就没有回归

### 缺陷点

本项目已有把纪律机检化的传统（配置审计抓"改配置不生效"，命名门禁抓"新代码不合口径"），
但**复用度不在任何自检里**：今天这 3 组重复块、0.702 的文件对、4 个路径谓词，没有任何东西能阻止
下个月变成 8 组、2 对、7 个谓词。新增一个"差不多"的辅助函数比复用它更快，因为它不需要理解既有实现；
而没有度量时，这种增量在 code review 里看起来完全正常。

### 改进后的预期效果

- 重复度有基线、有阈值、有豁免清单：`tools/dupcheck.py --check` 在自测里跑，超过基线即失败，
  并指出"新增的重复块在哪两处"。
- 数字只能变好或按豁免清单解释：每次改善都体现为基线数字下降，退化要写豁免理由。
- 想复用却找不到入口的人，有一条命令能告诉他"这件事仓库里已经有人做过"。

### 改进方案

1. `tools/dupcheck.py`（放仓库内，只用标准库，Python ≥ 3.4 可跑，与 `ci` 同档）实现 §〇 的三种度量：
   精确重复块（≥12 行）、函数级近似重复（0.82）、整文件相似度（0.45）。默认输出报告，`--check` 模式比对
   `.dupcheck-baseline.json`（记录本文表格里的当前数字）并在退化时以非零退出。
2. 豁免清单 `.dupcheck-allow.json`：现登记三项——两份 `audit.py`（理由见 F3，由对照测试代替合并）、
   `ci/stages/build.py` ↔ `build_test.py`（薄入口，见 §六）、`xfail.verdict`（待 F3 第 4 条覆盖）。
   每条必须有 `why` 字段，无 `why` 视为未豁免。
3. 复用入口：`tools/dupcheck.py --catalog` 列出 `ci/lib/*.py` 与 `standardize/.../*.py` 的公开函数签名
   （从 AST 取，不执行代码），按名字分组，供"这件事是不是已经有了"的一分钟查询。
4. 接入两侧自测（`ci/tests/run.py` 与 `standardize` 的 pytest 各一条），只检查生产代码，测试代码豁免
   ——测试里重复的 fixture 是有意的可读性选择，见 §六。

## 五、决定不做（写下来，免得下一个人重新提）

| 议题 | 决定 | 理由 |
| --- | --- | --- |
| 合并 `build.py` / `build_test.py` | **不做** | 两者相似度 0.875 但各只有 26/27 行，是**薄入口**：真正的流程在 `ci/lib/stage.py::run_stage` 与 `cli.stage_main` 里，已经是复用的正确形态。合并成"带参数的一个脚本"会让阶段可单独调用、单独调试的性质变差——那是这套工具的立身之本 |
| 再抽一套 SCOPE / 范围判定 | **不做** | 唯一入口 `paths.scope_of` 已存在且被 `stage.owned:275`、`valgrind:275`、`boundary:135`、`clean:49` 使用；F1 做的是**收口谓词**，不是再发明一层 |
| 为两份 `audit.py` 引入第三个共享包 | **不做** | 破坏"两个项目互不 import、各自独立部署"的架构约束；`ci` 侧 Python 3.4 上限也无法让共享包同时满足两侧。用 F3 的同固件对照测试达到同样目的 |
| 抽公共 `errors.py` / `output.py` / `config.py` | **不做** | 三个文件整文件相似度都 <0.45，实现与语义各自演化（错误码 16 位布局 vs `Code` 枚举、终端回显 vs 分级日志），合并只会把两种约定搅在一起 |
| 给测试代码抽公共 helper | **不做** | 测试里 ≥12 行重复 0 组、近似重复 0 对；测试 fixture 各自写是**可读性选择**，抽出来会让一个测试看不懂自己在测什么。F4 的度量显式只作用于生产代码 |
| 纯粹为长度拆函数 | **不做** | >60 行的只有 9 个，>100 行只有 2 个，都在本次要动的 `style.py` 里；不为长度单独开改动（拆函数会扰动门禁，收益要配得上风险） |

## 六、实施顺序

| 序 | 项 | 理由 |
| --- | --- | --- |
| 1 | F1 路径谓词收口（含软链回归测试） | 唯一可能导致"同一诊断在不同阶段结论相反"的项，改动小、收益直接 |
| 2 | F4 `tools/dupcheck.py` + 基线 + 豁免清单 | 先立度量，后面 F2/F3 的收口效果才可验证；也防止修完再长回来 |
| 3 | F2 `_prepare_run` 抽取（含 `prepare` 三入口一致、`--apply` 不完整要出声） | 已有规则漂移，且能顺带把两个最长函数拆短 |
| 4 | F3 同固件对照测试 + 豁免表 + 两侧文件头互指 | 不减少现有行为，纯加护栏；需要 F4 的豁免表当载体，故排其后 |
| 5 | F3 第 4 条：`xfail.verdict` 对照测试 | 同一套护栏的延伸 |

与前两篇提案的关系：

- 《改进提案 2》E1（源码编码与行尾收口）会改 `format.py` / `boundary.py` 的读写路径，`source.py` 一落地，
  本文 F2 在 `style.py` 里抽的前置就应改用 `source.read_source/write_source`——**E1 先做**，否则两处改动
  会互相覆盖。
- 《改进提案 2》E1 提的"禁止裸读写文本"审计与本文 F1 第 5 条（禁止自行前缀比较）、F4 的重复度自检，
  都属于同一类东西：把一次性的人工 review 变成每次门禁自动跑的纪律，建议一起设计在同一个自检入口里。
- 《改进提案》(D4) 的禁改区贯通与本文 F1 处理的是同一个归因链（路径判定 → 归属 → 是否计入门禁），
  应并批验收，避免同一个谓词被改两次。

## 七、边界与红线

- **收口不得改变判定结果**：F1 的谓词统一、F2 的前置抽取都属"行为不变重构"。唯一允许的有意行为变化是
  F2 第 3 条（派生文件未就绪时 `--apply` / `--record` 要出声），必须写进 CHANGELOG 并在测试里钉死。
- 收口后不得引入跨项目 import：`ci` 与 `standardize` 仍然只靠文件与命令行契约协作；standardize 侧需要
  同样的路径谓词时，用**平行实现 + 对照测试**（与 `audit.py` 同一策略），不 import `ci/lib/paths.py`。
- 对照测试比较的是**结论集合**（判据、相对路径、配置键三元的集合），不是输出的文字与顺序；否则对照测试
  会退化成"两条打印必须逐字相同"，第一次改文案就炸。
- 豁免清单不得当垃圾桶：每项必须有 `why`，且 F4 的 `--check` 要在豁免实际未被命中时报"豁免已失效，请删"
  ——过期豁免与缺失豁免同样危险。
- 度量脚本自身不碰网络、不装依赖、不改代码；`--check` 只读。若将来它需要第三方库（例如 chardet），
  就不配再放在 `ci` 的自测路径里（`ci` 侧零第三方依赖是硬约束）。
