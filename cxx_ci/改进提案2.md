# cxx_ci 改进提案 2（定位、接入与交付）

本文与《改进提案.md》并列，不重复它的内容。本文只写三件事：**缺陷点 → 改进后的预期效果 → 改进方案**，
外加一节"决定不做的事"。所有术语在本文内解释，读者不需要任何其他仓库或文档。

已定方向（本轮不再讨论，只按它设计）：

| 议题 | 决定 |
| --- | --- |
| 源码编码 | **要处理**（当前会静默写坏非 UTF-8 文件，P0） |
| 结果输出 | **要处理**：机器可读报告（P0） |
| 接入成本 | **要处理**：配置探测与失败解释（P1） |
| 交付形态 | **要处理**：版本化 + `requirements.txt` + 配置迁移（P1） |
| 运行平台 | **定位为 UNIX**：不做跨平台，但要把"只在 UNIX 上跑"变成显式约束（P2） |
| 构建工具面 | **维持 `cmake` / `qmake` / `qmake6`，不扩**（见 §六） |

## 〇、阅读前提

cxx_ci 是两个互不 import 的项目，只靠文件与命令行协作（契约登记在 `CONTRACT.md`，当前契约版本 2）：

| 项目 | 运行环境 | 依赖 | 职责 |
| --- | --- | --- | --- |
| `ci/` | Python ≥ 3.4 | **零第三方依赖**（只用标准库） | 阶段编排与门禁：`boundary` / `clean` / `build` / `build_test` / `run_test` / `memcheck` |
| `standardize/` | Python ≥ 3.11 | `PyYAML>=6.0`；可选 extra `clang17`（`clang-format==17.0.6`、`clang-tidy==17.0.1`，自带二进制，装上就优先于系统 clang 使用） | 排版（clang-format）、风格（clang-tidy）、命名（按口径表改标识符名） |

配置规模（本轮实测计数）：`ci/config/config.py.example` 有 **61** 个配置项，
`standardize/config/config.py.example` 有 **30** 个。

几个本文会用到的现有约定：

| 约定 | 现状 |
| --- | --- |
| 协议行 | 阶段脚本发给驱动层的机器可读行：`#diag <级别>: <文件>:<行>:<列>: <消息>`、`#fail: <用例> <原因>`、`#sum: <一行摘要>` |
| 阶段结论 | 三态：通过 / 失败 / `[SKIPPED]`（外部工具缺失时算跳过，**跳过不等于通过**） |
| `CI_LOG_DIR` | 每阶段完整输出落盘目录（缺省 `BUILD_DIR/ci-logs`），`clean` 会保留它 |
| 退出码 | 16 位错误码（高 8 位类型、低 8 位编号），进程退出时只取类型；跨进程用 `errors.compose` 还原 |
| 契约版本 | `ci` 与 `standardize` 各自声明 `CONTRACT_VERSION`；当前**只有 `run_all.sh` 比对两侧**，单独跑 `ci.py` 或 `cxx-standardize` 不校验 |

## 一、E1【P0】源码编码不探测，非 UTF-8 文件会被静默写坏

### 缺陷点

全仓库没有任何编码探测（搜 `chardet` / `GB18030` / 编码检测相关代码：无）。所有文本读取都是同一句
形状：

```python
data.decode("utf-8", "replace")     # 解不了的字节 → U+FFFD，不抛异常
```

只读的地方无所谓，**读写闭环的地方就是数据损坏**：

| 位置 | 读 | 写 |
| --- | --- | --- |
| `standardize/src/cxx_standardize/format.py:63` → `:78` | `read_bytes().decode("utf-8","replace")` | `once.encode("utf-8")` 整文件写回 |
| `ci/lib/boundary.py:105-107` → `:207-209` | 同上 | `handle.write(text.encode("utf-8"))` 整文件写回 |

于是一个 GBK / GB18030 编码的存量工程（国内 SVN 时代的老代码普遍如此，而 `ci` 侧的目标机器之一就是
CentOS 6 这类老系统）跑一次 `cxx-standardize format --apply` 或 `ci/stages/boundary.py --fix`，
**每一处中文注释、中文字符串字面量都会变成 U+FFFD**，而且：

- 不报错、退出码可以是 0（排版成功、构建判卷也过——U+FFFD 是合法字符，照样编得过）；
- 事后不可逆：原字节已经不在了，只能靠版本控制回滚。

这不是"效果不好"，是**工具会吃掉用户的代码**。同类风险面还有：`ci/lib/xfail.py:120`（清单读）、
`standardize/src/cxx_standardize/tidy.py:318`（`.clang-tidy` 读）、`ci/lib/output.py:37`（子进程输出解码，
只读所以安全）。

**同一读-写路径还必须保证换行符保真**：CRLF 的存量文件（Windows 编辑器、共享目录、混编仓库都常见）
经过"按行切分→重排→整体写回"这一串步骤后是否仍是 CRLF，现状**没有验证也没有断言**。这是与编码
同族的第二类静默改写，必须一起收口。

### 改进后的预期效果

- 任何被本工具写过的文件，**除排版/改名意图之外的字节不变**：编码不变、换行符不变、BOM 不变、
  文件末尾换行不变。
- 解不出编码的文件一律**只读**：诊断照报、`--apply` / `--fix` 对该文件跳过并明确说
  `编码无法确定（不是合法 UTF-8，且未配置 SOURCE_ENCODING）: <路径>，本文件不会被改写`，退出码按
  "有文件未完成"计（不是 0，也不是失败判卷）。
- 中文注释在 GBK 工程里跑 `format --apply` 后仍然是中文（回归测试覆盖）。
- 编码判定过程可解释：`doctor` 报告里能列出"按 BOM 判定 / 按 UTF-8 严格解码判定 / 按配置指定"三种来源
  各命中多少文件。

### 改进方案

1. **收口唯一的读写入口**：`standardize/src/cxx_standardize/source.py`（新）+ `ci/lib/source.py`（新），
   提供 `read_source(path, config) -> (text, SourceInfo)` 与 `write_source(path, text, info)`；
   `format.py`、`boundary.py`、`style` 的写入路径全部改走它，禁止再出现裸的 `read_bytes()`+`encode("utf-8")`。
   `SourceInfo` 携带 `encoding`、`newline`、`bom`、`had_final_newline`，写回时逐项还原。
2. **判定顺序**（`SOURCE_ENCODING` 配置项，缺省 `"utf-8"`，可写 `"auto"` 或显式编码名如 `"gb18030"`）：
   BOM → `utf-8` 严格解码（`errors="strict"`，失败即否定）→ 配置里 `SOURCE_ENCODING_CANDIDATES` 列出的
   候选逐个严格试（**默认空**：不猜 GBK，宁可跳过也不写坏）→ 全失败返回 `ENCODING_UNKNOWN`。
   显式写了 `SOURCE_ENCODING="gb18030"` 就按它 strict 解，解不动同样跳过。
3. **写前校验**（`write_source`）：用 `SourceInfo.encoding` 做 `text.encode(..., errors="strict")`，
   编码不下（例如 GBK 文件里出现了 GBK 表示不了的新字符）→ 拒绝写并列出 offending 行；与既有原则
   "读不出就不写"配成一对，杜绝"写一半"。
4. **换行与 BOM**：读取时记录 `newline`（`''` 模式打开即可保 CRLF），排版类改写必须逐行原样保留行尾；
   clang-format 的 `--assume-filename` 调用统一加 `--line-ending` 对齐实际行尾（或在还原阶段把行尾
   改回来，二选一，写清在 `source.py` 的注释里）。
5. **审计**：把"禁止裸读写文本"变成可机检的纪律——`ci/lib/audit.py` 的旁路检查已经会拿字面量与配置
   取值比对，扩一条：项目/自身源码里出现 `open(<path>, "w")` / `write_text(` / `encode("utf-8")`
   且不在 `source.py` 白名单内 → 判红。这样后来人不会又写回裸调用。
6. **测试**（两侧各一份）：造一份 GBK 编码、带中文注释、且**注释是手工对齐**的源文件，
   ①`format --apply` 后原字节除空白/换行外逐字节相同，中文仍在；②`SOURCE_ENCODING` 未配时该文件被跳过
   且退出码非 0；③CRLF 文件跑完仍是 CRLF。

## 二、E2【P0】没有机器可读的结果出口

### 缺陷点

驱动层的结论只有三种去处：协议行回显（按 `--level`）、落盘日志（`CI_LOG_DIR/<阶段>.log`）、进程退出码。
**没有 JSON / JUnit / SARIF 任何一种报告文件**（全仓搜 `junit` / `sarif`：只在"有意不采用外部报告器"
的说明与测试适配器代码里出现，那是**输入**方向——解析测试框架输出，不是**输出**方向）。

后果是接不进任何 CI 平台的原生面板：

- Jenkins / GitLab CI / GitHub Actions 都需要 `junit.xml` 之类才能做用例趋势、失败归因、flaky 标记；
  现在只能把整段终端文本塞进 job log，趋势与失败率全靠人工看。
- clang-tidy / 编译器诊断进不了代码评审界面（GitHub/GitLab 认 SARIF 才能把告警贴到 diff 行上）；
  而本工具已经算出了比 SARIF 要求更准的归属（项目内 / 第三方 / 系统库），这些信息现在被压成文本丢掉。
- 已登记的存量问题（`ci.xfail`、`standardize.xfail`）在文本里只是一个 `(xfail)` 后缀，平台侧无法把它
  显示成"已知"而不是"失败"或"通过"。

数据其实齐了，缺的只是一个 sink。

### 改进后的预期效果

- `python3 ci/ci.py --report=build/ci-report.json`（可 `--report-format=json|junit|sarif`，可逗号并列，
  可 `--report=-` 打到 stdout）产出一份与终端判定**完全同源**的报告文件。
- 三态在报告里仍是三态：`skipped` 带原因，不会塌成 `passed`；xfail 条目带"已知"标记，既不算失败也不算
  通过；`unfixable`（工具不提供修复项）单独计数，不会看起来像"没干活"。
- 平台能把诊断直接标到文件行：SARIF 里 `region.startLine/startColumn` + `rule.id`（clang-tidy 检查名或
  编译告警 `-W` 名）齐备；JUnit 里每阶段一个 `<testsuite>`、每条失败用例一个 `<testcase>`。
- 报告可 diff：两次运行的报告做 diff 能直接回答"这次多了哪几条诊断/少了哪几条用例"，这是门禁最常被问
  的问题，现在只能靠肉眼看日志。
- 报告带来源指纹：工具与版本、clang 可执行文件与版本、生效配置的关键取值、基线指纹——用于排查
  "同一份代码在两台机器上结论不同"。

### 改进方案

1. **内部先有一份 schema，再谈三种格式**：新增 `ci/lib/report.py`，定义与契约版本一起登记的 JSON schema
   （`report_version` 字段自管），形状大致：

   ```json
   {
     "report_version": 1, "tool": {"ci": "1.3.0", "standardize": "1.2.0", "contract": 2},
     "environment": {"python": "3.11.9", "clang_format": "/usr/bin/clang-format-17", "clang_version": "17.0.6"},
     "config_digest": {"SCOPE": ["Source/App"], "MEMCHECK_TOOL": "asan", "DIAGNOSTIC_LEVEL": "warning"},
     "baseline": {"format_fingerprint": "…", "xfail_file": "ci.xfail", "xfail_count": 12},
     "stages": [{"name": "build", "status": "passed", "seconds": 3.6,
                 "diagnostics": [{"level": "warning", "file": "…/Logger.cpp", "line": 528,
                                  "column": 1, "message": "…", "check": "-Wunused-function",
                                  "owner": "project", "count": 1, "xfail": false}],
                 "summary": "1 条诊断（过滤 607 条）", "log": "build/ci-logs/build.log"}]
   }
   ```

   取值全部来自既有的协议行、阶段结果对象与归因结果，**不新增任何判定分支**——报告只做搬运，
   判定仍由阶段负责。这样"报告说绿、终端说红"在结构上不可能发生。
2. **三个 writer**：`report.py` 内 `to_junit()` / `to_sarif()` / `json`（默认）。映射规则写死在文档里：
   JUnit 的 `<skipped message>` 承载三态，`owner != project` 的诊断不进 JUnit（否则面板被第三方噪声淹没）；
   SARIF 用 `partialFingerprints`（文件 + 检查名 + 消息摘要）保证同一条告警跨运行可比，`xfail` 映射为
   `baselineState: "unchanged"` + `properties.knownIssue = true`。
3. **`standardize` 侧同形状**：`cxx-standardize` 加同一对 `--report` / `--report-format`，产出同一份
   schema（把 style 诊断、命名诊断、"需人工"文件清单、`unfixable` 计数装进 `stages`）；schema 作为
   `CONTRACT.md` 的新契约项登记，两侧共用一份 JSON 就是共用一份定义，不需要共享代码。
4. **退出码语义不动**：报告是旁路产物，`errors.py` 的 16 位错误码与"退出取类型"的规则保持不变；
   写报告自身失败（目录不可写等）只降级为警告 + 非零诊断计数，不改变门禁结论。
5. **测试**：一个阶段结果对象 → 三种格式的黄金文件断言；专项断言"skipped 不塌成 passed"、
   "xfail 既不是 failure 也不是 pass"、"两份报告的诊断集合与终端输出的协议行一一对应"。

## 三、E3【P1】接入成本是"好用"的天花板

### 缺陷点

`ci` 侧 61 个配置项、`standardize` 侧 30 个，其中真正必需的是 2 个（`ROOT`、`BUILD_TOOL`），其余都有
推导缺省——这一点做得好。问题在**剩下的项什么时候必须动、动了会怎样，只有读源码和 README 才知道**：

- 内存检查最容易红，而收敛手段散在 4 个调参项上（`MEMCHECK_IGNORE_KINDS`、`MEMCHECK_REPEAT`、
  `MEMCHECK_IGNORE_SYMBOLS`、`MEMCHECK_SCOPE`），彼此还有"缺一不可"的组合关系；
- `TIDY_HEADER_FILTER` / `.clang-tidy` 的 `HeaderFilterRegex` 写宽一个字符，诊断能从 67 条涨到 5501 条；
  写窄则把工程自己的头文件的诊断静默藏掉。这类"配错不报错"的项，新人第一次接入必然踩；
- 失败时的输出是**结论**而不是**下一步**：`[FAILED] memcheck`、`style 未通过` 之后，用户仍要自己去
  翻 `CI_LOG_DIR` 与源码才知道该改哪一项。

《改进提案.md》D4/D5 修的"报错不指路"是这条的冰山一角；根治要让工具自己会解释。

### 改进后的预期效果

- **接入一个新工程 = 三条命令**：`ci.py init` → `standardize.py init` → `ci.py doctor`。前两条产出的
  配置带逐项依据注释，人只需复核而不是从零写；第三条在任何时候都能回答"现在生效的是什么、为什么红、
  下一步跑什么"。
- 配置项在文档与 `--help-config` 里分三层：**必需**（2 项）/ **常用**（构建、测试、范围、内存路线，
  约 15 项）/ **调参**（归因与抖动，其余）。调参层每一项都写"什么时候才需要动它"和"动完怎么验证"。
- 高危项（`TIDY_HEADER_FILTER`、`HeaderFilterRegex`、`SCOPE`、`MEMCHECK_*`）在取值明显失当时就地提醒：
  例如 header-filter 会命中构建树外的第三方 include 根 → 直接给出建议写法（`include/<工程名>/.*`）。
- 首次接入不再需要"先跑一天调门禁"：`doctor` 会给出一条建议命令，把当前未登记的违规一次性落成基线
  （即 `standardize.py style --record` 与 `ci.xfail` 的写入），门禁当天变绿、以后只对新问题判红。

### 改进方案

1. `ci/stages/../ci.py init [--project-root PATH] [--out config/ci.py]`（探测逻辑放 `ci/lib/probe.py`，
   新）：
   - 构建工具：找 `CMakeLists.txt` / `*.pro` / `*.pri`（多份时列出候选让人选，**不猜**）；
   - 构建目录、测试构建目录：按 `BUILD_DIR` 惯例与已有影子目录识别；
   - 测试指令：`CMakeLists.txt` 里有 `enable_testing()`/`add_test` → `ctest --output-on-failure`；
     `tests.pro` 存在 → `make -C <测试树> check`；否则留 `TEST_COMMAND = []` 并写注释说明"这条留空则
     `run_test`/`memcheck` 标 `[SKIPPED]`"；
   - `SCOPE`：从版本控制跟踪的源码目录取（无 git 时退回 `src` / `include` / `tests` 命名惯例），把
     `third_party` / `vendor` / `external` / `build*` 放进 `excluded`；
   - 编译标准：从构建文件里读（`CMAKE_CXX_STANDARD` 或 `.pro` 的标准变量）读不到就留空并注释；
   - 每一项写成 `<值>   # 依据: <命中了什么>`，探测不到写 `# TODO: 需要人工填写（缺 <什么信息>）`。
2. `cxx-standardize init [--out config/standardize.py]`：检查 `.clang-format` / `.clang-tidy` 是否存在
   （缺了就给最小模板，并说明"配置不存在会被直接拒绝、不退成逐级向上查找"这条既有规则）、探测
   `CLANG_MAJOR`、按工程 include 形状产出 `TIDY_HEADER_FILTER` 建议、识别 vendored 目录填 `FROZEN`
   （判据：名字命中 `third_party|vendor|external` 或含 `LICENSE` 且无本工程构建文件）。
3. `doctor` 子命令（两侧各一份，`ci` 侧汇总 `standardize` 的结论）输出四段、每段一屏内：
   ①**环境**：Python、构建工具、`clang-format` / `clang-tidy` 的实际路径与版本（含是否来自 pip 包）、
   `valgrind` / `libasan` 可用性；②**生效配置**：关键取值 + 每项来源（配置文件 / 推导 / 缺省）；
   ③**上次结论**：从 `CI_LOG_DIR` 与 E2 的报告读回，按"哪一类、哪个符号前缀/检查名"聚合；
   ④**下一步**：具体命令（例如 `cxx-standardize style --record` 或 `MEMCHECK_REPEAT=2`），
   而不是让人去猜配置名。
4. **配置元数据化**：把每项的"必需性 / 一句话语义 / 未写时的推导规则 / 什么时候要动"写进
   `ci/lib/config.py` 的一项表（字典元数据），`config.py.example` 的分节与 `--help-config` 都从它生成；
   example 与元数据由一致性测试钉住（少一项即测试红），杜绝文档漂移。
5. **高危项就地提醒**：`config.load` 之后做一次"建议性检查"（只打印，不判红）：header-filter 命中
   构建目录或外部 include 根、`SCOPE.excluded` 没排除构建目录、`MEMCHECK_SCOPE=all` 且没配忽略集等。

## 四、E4【P1】没有"库"意义上的交付形态（含 `requirements.txt`）

### 缺陷点

| 方面 | 现状 | 后果 |
| --- | --- | --- |
| 版本 | `standardize.py --version` 打工具版本与 `contract: 2`；`ci.py` **没有** `--version`；两处都没有语义化版本号，也没有 CHANGELOG | 出问题无法定位"哪一版开始"；跨工程分发（工具常作为子模块/独立检出引入）时只能靠 git commit 说事 |
| 契约校验 | 只有 `run_all.sh` 比对两侧 `CONTRACT_VERSION` | 只用 `ci.py`（老机器日常门禁）或只用 `cxx-standardize`（现代机器风格检查）时，**取自不同代的两侧不会被发现**，而它们的文件/命令行契约未必还对得上 |
| 依赖声明 | `standardize/pyproject.toml` 里 `PyYAML>=6.0`，可选 extra `clang17` 带 `clang-format==17.0.6`、`clang-tidy==17.0.1`；**没有 `requirements.txt`** | 没有能直接喂给 `pip install -r` / 离线镜像 / 内部审计的清单；老机器（无网、CentOS 6）拿不到"这一版工具到底需要什么"的答案 |
| 可选 clang 包的优先级 | 装上 pip 的 clang 包就**优先于系统 clang** 使用 | 团队里装了 wheel 的机器与没装的机器排版结果不同；主版本号相同不代表来源相同（与《改进提案.md》D6 同一问题，这里是策略侧的一半） |
| 配置迁移 | 旧名 `WHITELIST` / `BLACKLIST` 改成 `SCOPE` 只有"提示一次"，没有改写工具 | 版本升级后各项目配置各自漂移，改一半的配置文件留在仓库里 |
| 安装说明 | README 里散见 `pipx install` / "拷目录即可" | 老机器无网场景（只拷 `ci/` + 一份配置）与现代机器 pipx 场景没有一份可照抄的安装手册 |

### 改进后的预期效果

- 两侧各自有语义化版本（工具版本与契约版本分开，各自演进），`ci.py --version` 与 `cxx-standardize --version`
  输出同一形状：`<项目> <x.y.z> contract <N> python >=<下限>`；`--report` 的 `tool` 段里也带这两个值，
  报告文件自证"是哪一版跑出来的"。
- 两个项目各一份 `CHANGELOG.md`，按"Added / Changed / Fixed / Removed + 契约影响"记；每次改协议行、
  配置项、退出码都必须写一条。
- 仓库根有 `requirements/` 目录，四条清单都能直接 `pip install -r`，且与 `pyproject.toml` 由一条测试
  钉住不漂移；`doctor` 的环境段直接引用它们做校验（缺包/版本越界点名）。
- 只用一侧入口时也会校验契约：`ci.py` 启动时把配置里的 `CONTRACT_VERSION` 与自身声明比对，不一致退出码
  2 并说明"配置/工具取自不同代，请对齐"；`run_all.sh` 退化为纯编排。
- 升级配置有工具：`ci.py migrate-config` / `cxx-standardize migrate-config` 打印将改写的 diff、写前落
  `.bak`，改完提示需要复核的项；旧名不再"提示一次"而是可一次性改干净。
- pip clang 包的优先级变成显式可配（`CLANG_PREFER` = `system|wheel|报错`），默认与团队约定一致，
  `doctor` 一屏能看清实际用了哪一份。

### 改进方案

1. **版本**：`ci/lib/version.py` 与 `standardize/src/cxx_standardize/version.py` 各放
   `__version__` 与 `CONTRACT_VERSION`；`ci.py` 加 `--version`；两份 CHANGELOG 建立，第一条就是本次改动。
2. **`requirements/`**（内容随 `pyproject.toml` 生成，不手抄）：
   - `requirements/ci.txt`：**空清单 + 头注释**——"本侧零第三方依赖，Python ≥ 3.4；本文件用于占位与审计，
     任何被加进来的包都应视为违反设计"。它的价值是让"零依赖"成为可被 `pip` 与审计看见的事实。
   - `requirements/standardize.txt`：`PyYAML>=6.0,<7`（与 `pyproject` 同源；上界补 `<7`，避免大版本 surprise）。
   - `requirements/standardize-clang17.txt`：`clang-format==17.0.6`、`clang-tidy==17.0.1`，头注释写明
     "只在机器上没有系统 clang 17 时安装；装上即优先使用，需要系统 clang 时配 `CLANG_PREFER=system`"。
   - `requirements/dev.txt`：`pytest>=8`、`ruff>=0.6`、`mypy>=1.11`（与现有 dev extra 同源）。
   - 生成与校验：`tools/export_requirements.py` 从 `pyproject.toml` 生成；新增一条测试断言"两者一致"，
     防止两份清单各自漂。
3. **契约校验下移**：`ci/lib/config.py` 与 `standardize` 的 config 加载里各加一次
   "配置声明的 `CONTRACT_VERSION` == 自身声明" 检查（配置没写则取工具缺省并静默通过，保持现在
   "项目可选覆盖"的语义）；`run_all.sh` 里那段版本比对删掉，只留编排与调用。
4. **`migrate-config`**：两侧各一个子命令，规则表驱动（旧项名 → 新项名 / 旧取值 → 新取值）；改写前先
   `--dry-run` 打印 diff，落盘前写 `.bak`，改写后把"需要人工复核"的项名列出来。与 E1 的原则一致：
   解不出编码或规则有歧义就不写。
5. **文档**：新增 `INSTALL.md`，按三种场景写死步骤——①老机器无网：只拷 `ci/` + `config/ci.py`，
   零安装；②现代机器：`pipx install ./standardize` + `pip install -r requirements/standardize.txt`；
   ③需要钉 clang 版本：再加 `requirements/standardize-clang17.txt` 并设 `CLANG_PREFER`。README 的
   依赖一节改为指向 `requirements/`，不再在正文里手抄包名。

## 五、E5【P2】把"只在 UNIX 上跑"变成显式约束

### 缺陷点

工具事实上依赖 POSIX 语义，但没有任何一处把它写成约束：内存检查只有 `valgrind` 与 ASan/LSan（都是
GNU/Linux 专属，ASan 运行库还靠 `g++ -print-file-name=libasan.so` 定位）、子进程与信号处理、
`LC_ALL=C` 的输出前缀、路径与软链假定。**在 Windows（含 WSL 之外的原生 shell）或 macOS 上，用户会
撞到"阶段一路 `[SKIPPED]`、内存检查静默不可用"这类半死不活的状态**，而不是被告知"本平台不支持"。

与其假装可移植然后到处降级，不如把定位钉死：UNIX（GNU/Linux 为主，BSD 尽力、macOS 只保证排版与风格）。

### 改进后的预期效果

- 在不支持的系统上，`ci.py` / `cxx-standardize` 在**做任何事之前**以退出码 2 退出，一句话说清支持面
  与例外（排版与风格检查在 macOS 可用；内存检查只在 GNU/Linux 可用）。
- 支持面在 README、`CONTRACT.md`、`doctor` 三处措辞一致，不再出现隐含假定。
- 细分降级：macOS 上跑内存检查 → `[SKIPPED]` + 原因；BSD 上跑 valgrind → 正常；不是"整条流水线全红"
  也不是"全绿但其实什么都没检查"。
- 代码里不再有硬编码 `/` 路径分隔或 POSIX-only 调用的漏网（少数例外集中在一处并写明）。

### 改进方案

1. `ci/lib/platform.py`（新）+ `standardize` 侧同名模块：`supported()` 返回 `(级别, 原因)`，级别
   `full`（GNU/Linux）/ `limited`（macOS/BSD：无内存检查）/ `unsupported`（其余）；`limited` 时把依赖
   专属工具的阶段标 `[SKIPPED]` 并带上 `STAGE_UNAVAILABLE` 错误码（复用现有"跳过不等于通过"机制），
   `unsupported` 时两个入口启动即退。
2. 平台判定只看 `os.uname()`/`platform.system()` 与"能否真的跑出工具版本"（探测优先于查表），避免
   发行版命名差异误判。
3. 文档收口：README 顶部一句"支持面"、`CONTRACT.md` 登记 `SUPPORTED_PLATFORMS` 为契约项、`doctor`
   环境段落打印级别与判据；配置项 `SOURCE_ENCODING`（E1）与 `CLANG_PREFER`（E4）一并进入契约登记。
4. 静态审计：扩 `ci/lib/audit.py`（或加一条自检测试）拦裸 `"/"` 拼接与未过 `platform.py` 的平台分支。

## 六、决定不做（写下来，免得下一个人重新提）

| 议题 | 决定 | 理由 | 如果将来要改 |
| --- | --- | --- | --- |
| 构建工具面 | 维持 `cmake` / `qmake` / `qmake6` 三种（`ci/lib/config.py:35` `BUILD_TOOLS`） | 这三档已覆盖"现代 cmake 工程"与"两代 qmake/Qt 工程"——也正是老机器上的全部真实形态。每加一种构建工具就多一套配置注入、影子目录、编译数据库与并行语义的分支，边际收益低于回归成本 | 唯一扩展入口是把 `ci/lib/build.py` 改成像 `DB_PROVIDER` 那样的 provider 注册表（`configure()` / `compile()` / `compile_db()` 三件事），新工具只加 provider，不碰阶段编排 |

## 七、实施顺序

| 序 | 项 | 为什么这个位置 |
| --- | --- | --- |
| 1 | E1 编码与行尾收口（`source.py` + 审计 + 测试） | 唯一会造成代码不可逆损坏的项，其余一切"写文件"的功能都依赖它才敢用 |
| 2 | E2 报告 schema 与三个 writer | 后面 E3 的 `doctor`、E4 的报告指纹都要读它；先定 schema，避免两处各造一份结论结构 |
| 3 | E4 版本 / `requirements/` / 契约校验下移 | 成本最低、且让后续每一项改动都能被 CHANGELOG 与版本号定位 |
| 4 | E3 `init`（探测生成配置） | 依赖 E4 的版本信息写进生成的配置头（生成的配置要注明由哪个版本产生） |
| 5 | E3 `doctor` + 配置元数据化 + `--help-config` | 把 E3 剩下的"会解释"补齐，与 D4/D5（另一份提案）的报错指路合并验收 |
| 6 | E5 `platform.py` 与支持面文档收口 | 纯约束显式化，不挡功能 |
| 7 | E4 `migrate-config` | 需要 E3 的配置元数据表当规则来源，故最后 |

与《改进提案.md》的衔接：那份提案的 D2（参数校验）与 D1（排版还原与自检）**排在本文 E1 之后、E2 之前**
执行——D1 改的正是 `format.py` 的读写路径，E1 的 `source.py` 一落地，D1 的改动就落在同一处，顺序颠倒
会互相覆盖。D4（禁改区贯通）与 D5（内存检查推导）与本文 E3/E5 同属"接入第一天"，可并批验收。

## 八、边界与红线

- `ci/` 继续 Python ≥ 3.4 且零第三方依赖：E1、E2、E3、E5 的实现只能在标准库内（`json` 标准库可用）。
- `standardize/` 不为老机器降格，可用 3.11+ 语法与 `requirements/standardize.txt` 里声明的依赖。
- 两个项目之间只有文件与命令行契约：E2 的报告 schema、E4 的 `SUPPORTED_PLATFORMS`、E1 的
  `SOURCE_ENCODING` 都作为 `CONTRACT.md` 登记项落地，靠"共用一份定义"对齐，不 import 对方代码；
  `run_all.sh` 仍是唯一同时看得见两侧的编排脚本，不得 import 任一侧内部模块。
- **报告不得成为第二个判卷人**：E2 的 writer 只允许搬运阶段结论，任何"在 writer 里补判定"的写法一律
  拒绝——否则终端与报告迟早会打架。
- **任何写文件的路径都必须过 E1 的 `source.py`**，并且遵守"读不出编码 / 写不回原编码就不写"；
  这条与"跳过不等于通过"同属工具可信度的地基，不接受为图快而开旁路。
- 项目配置不进工具目录：`init` 生成的是 `<工程>/config/ci.py`、`<工程>/config/standardize.py`，
  工具自带的只有 `config.py.example`。


# cxx_ci 改进提案 3（复用度与重复）

本文回答一个问题：**cxx_ci 的代码是否存在"相似逻辑很多却没提取"的问题。**
回答基于可复现的度量，不基于印象；所有数字给出测量口径，读者可用同样口径复核。
写法沿用前两篇：**缺陷点 → 改进后的预期效果 → 改进方案**，末尾给出"决定不做的事"。
