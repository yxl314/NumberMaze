# 当前问题分析

本文说明 cxx_ci 现在处于什么状态、卡在哪里、以及把卡点解决之后项目会变成什么样。
结论先行：**门禁本身（`ci`）已经可用且三个真实工程全绿；自动修复只完成了一半——
排版与非命名的风格修复已经能自动做完，变量命名还不能，而后者正是"工具是否值得
用"的关键。**

---

**体例约定**：本文每一节的结论都必须带"验证日期 + 复现命令"；实现推进后旧结论
要么改写、要么移入"历史与踩坑"。**没有验证日期的小节视为结论已失效**——本文曾经
就因为落后于实现，把"命名做不到"写成了现状，读者照着它去设计新的改名引擎，而
引擎早就在 `prefix.py` + `style.py` 里了。

## 一、当前现状

### 1.1 工具本身

两个互相独立的项目，只靠文件系统与命令行耦合（见 `CONTRACT.md`，契约版本 **2**）：

| 项目 | 语言要求 | 依赖 | 职责 |
| --- | --- | --- | --- |
| `ci/` | Python ≥ 3.4 | 零第三方依赖 | 构建、测试、内存检查、内部面边界、配置审计 |
| `standardize/` | Python ≥ 3.11 | PyYAML | 排版（clang-format）、风格与命名（clang-tidy） |

- 错误码统一 16 位：高 8 位类型、低 8 位具体编号，全程用 `(值, 错误码, 说明)` 三元组，不用异常做控制流。
- `ci` 阶段固定为 `boundary / clean / build / build_test / run_test / memcheck`；跳过（`[SKIPPED]`）与通过、失败是三个不同结论。
- 测试：本机 **566 通过**（ci 423 + standardize 143）；el6（CentOS 6.10 / Python 3.4.10）**423 通过 + 冒烟通过**。
- `规则清单.md` 自检脚本全绿（注释自足、无静默吞异常、无死代码、同概念同做法等 12 条）。

### 1.2 三个实战工程

`singleproc`、`stacklog`（cmake + ctest + valgrind）、`qtproj`（qmake + Qt 5.6）三个真实
工程都装上了团队规范（`.clang-format` 121 行、`.clang-tidy` 303 行逐字采用），配置放在
工程自己的 `config/ci.py` 与 `config/standardize.py`（工具目录是子模块，配置写进去提交
不到工程、重拉工具还会覆盖）。

**门禁侧三个工程全部全绿：**

| 工程 | `ci` 六阶段 | 说明 |
| --- | --- | --- |
| singleproc | 全绿 | boundary / clean / build / build_test / run_test / memcheck |
| stacklog | 全绿 | 同上；fork 类用例按配置排除内存检查 |
| qtproj | 全绿 | 同上；Qt 5.6 在 clang 17 下的已知误报已按配置屏蔽 |

**风格侧剩余诊断：**

| 工程 | 剩余 | 其中命名类 | 非命名类 | 命名类构成 |
| --- | --- | --- | --- | --- |
| singleproc | 55 | 49 | 6 | 成员 21、参数 17、枚举值 10、全局常量指针 1 |
| stacklog | 490 | 485 | 5 | 参数 332、成员 124、静态变量 8、枚举值 7、constexpr 6 |
| qtproj | 67 | 67 | 0 | 参数 48、方法 8、局部变量 5、全局函数 5、成员 1 |

即：**剩下的一千条里 99% 是命名类**，非命名类已经基本修完（且都是 clang-tidy 没有
fix-it 的那几种，见 2.4）。

### 1.3 已经能自动做完的部分

- **排版**：`clang-format --apply` 一次性完成，含注释保护（先占位再还原，注释内容
  与手工列对齐不被破坏）。
- **非命名的风格修复**：`cxx-standardize style --apply` 自动修完，逐文件用构建验证
  （`VERIFY_COMMAND`）兜底，改坏了立刻回退。实测 stacklog 一轮修掉 21 个文件、
  230 条诊断（花括号、冗余成员初始化等），构建仍然通过。
- **门禁的自动修复**：编译标准漂移、头文件宏守卫（`boundary.py --fix`）都能自动修。

## 二、遇到的问题

按严重程度排序。前两个是**已经查清并修掉**的，第三个是**当前的主要卡点**。

### 2.1 自动修复"报告成功，实际一个文件都没改"（已修）

**现象**：`--apply` 打印 `全部文件已符合风格`，退出码 0，但 `git status` 一个文件都
没变；紧接着单独跑一次 `check`，仍然是 506 条。

**根因**：为了在自动修复时关掉命名检查，实现用了命令行的 `--checks`。但
`--checks` 是**覆盖**而不是追加——必须把 clang-tidy 的完整生效列表一字不差地复现
出来。复现的那份漏了 clang-tidy 自己补的 `clang-diagnostic-*`，逗号后面还带着空格，
整份列表解析不出来，clang-tidy 一条诊断都不报。

**为什么这个最严重**：它把"什么都没做"伪装成"全部符合"。使用者会以为代码是干净的，
而门禁在下一个进程里又是红的——比直接报错危险得多。

**修法**：改成写一份派生配置（改 `Checks` 文本），不再用命令行覆盖。

**连带的第二个坑**：`yaml.safe_dump` 默认在 80 列折行，`Checks` 这种长标量会被写出
换行，而换行符会成为取值的一部分，同样让 clang-tidy 读不出检查列表。写配置时一律
关掉折行。

### 2.2 自动修复缺少构建验证时能写出编译不过的文本（已修）

**现象**：没有配 `VERIFY_COMMAND` 时，clang-apply-replacements 把两处重叠的 fix-it
叠在一起，写出：

```cpp
t_max_message_bytes(static_cast<std::size_t>(1024 * )1024)
```

**修法**：`--apply` 现在**要求**必须有构建验证指令，缺了直接拒绝并说明原因，而不是
提醒一句就往下走。

### 2.3 变量命名无法自动收敛 —— **已解决**（2026-10，见 §2.9）

> 本节保留的是**当时的判断**，它已经不成立。现在的做法：命名路径用项目自己的
> `.clang-tidy` 做检测，按口径表 `NAMING_PREFIX` 算目标名（clang-tidy 给的
> `_bad_local` 会被回改成 `bad_local`），跨翻译单元收集替换后一次性应用，末尾用
> `VERIFY_COMMAND` 判卷、不过整体回滚。详见 §2.9。

clang-tidy 的 `readability-identifier-naming` 修复有三个先天缺陷，每一条都有实测
证据：

| 缺陷 | 实测证据 | 后果 |
| --- | --- | --- |
| 只改**被分析的那一个翻译单元**里的引用 | 成员在头文件里声明、在 `.cpp` 里使用：头文件那一趟只产出声明处的替换 | 改了声明没改使用，工程编译不过 |
| 声明在**被包含**的头文件里时，干脆不产出替换 | 同一个头文件：当主文件分析给 1 处替换；被 `.cpp` 包含时给 **0 处** | 想补都无从补起 |
| 只会"套用 Case+Prefix" | `v_local` → `_v_local`、`m_wrong` → `_m_wrong`、`s_static` → `_s_static` | 对"去前缀"类违规产出的是垃圾，不是修复 |

结果就是：`--apply-naming` 每轮只能前进一小步（stacklog 506 → 490），大部分文件因为
"改完编译不过"被回退转人工。

**为什么不能靠"多跑几轮"绕过**：改名是跨文件的原子操作。头文件里的声明一改，包含它
的所有 `.cpp` 立刻编译不过，clang-tidy 连分析都做不了，第二轮无从谈起。

### 2.4 非命名类残留的都是"clang-tidy 没给 fix-it"的检查

剩下 11 条非命名诊断分布在 `performance-unnecessary-copy-initialization`（5）、
`bugprone-implicit-widening-of-multiplication-result`（2）、`bugprone-empty-catch`（3）
等检查上——这些检查本身就只报告不修复，属于工具能力边界，不是配置问题。

### 2.5 缺少符号感知的改名引擎 —— **已不需要**（2026-10）

> 结论已被推翻：位置由 clang-tidy 提供（跨 TU 的每一处出现它都指得出来），文本
> 由 `prefix.py` 按口径表算，两者拼起来就是符号感知的改名，不必依赖
> `clang-rename`。见 §2.9。

真正能解决 2.3 的是"按符号改名"：定位一个符号，把它在全工程的所有引用一次改掉。
LLVM 官方的 `clang-rename` 正是干这个的，但本机这套 clang-17 只装了
`clang-format` / `clang-tidy` / `clang-apply-replacements`，没有它（且它在 LLVM 18
起已被移除）。

### 2.6 本轮试过但没跑通的两条路线（记录在案，避免重蹈）

1. **先收集所有翻译单元的修复、再一次性应用**：目的是让跨文件改名在同一轮里一致。
   实测仍然收敛不了——2.3 第二条决定了"收集不到就是收集不到"。
2. **按角色补完 clang-tidy 没给全的改名**：从全局收集"角色 → 旧名 → 新名"，再按每个
   翻译单元自己的诊断判断那个词在该单元里是参数还是成员，取对应目标名做整词替换。
   判定不稳，改完仍会编译不过。

两条都已撤掉（留着就是死代码）。

### 2.7 配置层面的坑（已在三个工程里修掉，但会再遇到）

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| `HeaderFilterRegex` 写太宽 | `(include\|src\|tests)/.*` 把 `/opt/qt-5.6.3/include/...` 一起放进来，qtproj 从 67 条涨到 **5501** 条 | 写 `include/<工程名>/.*` |
| `DETAIL_DIRS` 照抄形状 | stacklog 的 `detail` 是**整个** `src/`（门面在 `include/`），按"只在自己子目录"配会误报 48 处 | 按工程内部实现层的实际范围配 |
| 局部变量被自动加前缀 | 规范要求局部变量裸名，而 clang-tidy 会给它硬加 `_` | 派生配置里清空局部类的 Prefix |
| qmake 测试构建目录 | 测试工程按相对路径引用主构建的静态库，与主工程共用目录会解析错 | 单独配 `TEST_BUILD_DIR` |
| 契约版本当成项目必填 | 项目不写就被判成"取自不同代" | 由工具实现声明，项目可选覆盖 |

### 2.8 一个绕不开的产品问题：门禁长期红，工具就没有意义

这是用户直接提出的关切。现状是：三个工程的风格门禁**都是红的**，且红的部分主要是
命名类——按规范要求命名必须人工改（规范自己写明了理由），于是"跑一次就好"的预期
落空。

工具已有的应对机制是 `standardize.xfail`：逐条登记已知违规，只对**新增**违规判红，
`XFAIL_STRICT` 防止清单腐化。这条链路是完整接好的，但目前没有"一键把当前违规登记
成基线"的入口，需要人工写清单。

### 2.9 命名自动化：现状与当初判断的差别（2026-10 验证）

**结论**：命名已经能自动收敛，不再是卡点。当初写 §2.3/§2.5 时看到的三条
"clang-tidy 做不到"，现在都有对应机制：

| 当初的障碍 | 现在怎么办 |
| --- | --- |
| 修复只覆盖被分析的那一个翻译单元 | 每个 TU 只读导出 → 按字节偏移合并去重 → 一次性原子应用 |
| 声明在被包含的头文件里时不产出替换 | 只跑 `.cpp` 并放行 `--header-filter`，声明处的改名由包含它的 TU 带出来 |
| 只会加前缀、不会脱前缀 | 位置用它给的，**文本按口径表自己算**（`prefix.py`）：`s_g_digits` → `s_digits` |
| 改名改挂测试（断言里写着旧名字） | 库里另有同名字面量时不同步测试字符串；`SIGNAL`/`SLOT` 宏单独同步 |

**复现命令**（三个真实工程，从各自未改名的原始状态）：

```bash
python3 cxx_ci/ci/ci.py --config config/ci.py --only build,build_test   # 先构建
python3 cxx_ci/standardize/standardize.py --config config/standardize.py --apply
python3 cxx_ci/standardize/standardize.py --config config/standardize.py  # 复查
```

实测：singleproc 61 → 2、stacklog 510 → 3、qtproj 68 → 0，`ci` 六阶段全绿。
剩下的全是 clang-tidy **不提供修复块**的检查（`--export-fixes` 的 `Replacements`
为空，逐条确认过），走 `--record` 登记基线。

**§2.6 那两条"试过撤掉"的路线**：第一条（先收集所有 TU 再一次性应用）**没有错**，
现在用的就是它——当初判定失败是因为收集方式用错了（把头文件当独立主文件跑，
自然收不到）。第二条（按角色补完 clang-tidy 没给全的改名）确实撤掉了，因为它的
判定不稳，而且现在的前缀规范化已经覆盖了它想解决的问题。

**验证日期**：2026-10。**复现命令**：见上。

### 2.10 一条流程事实：standardize 必须在构建之后、清理之前跑

编译数据库是构建的产物。`ci` 的完整流程结束会清掉构建树，数据库随之失效；
`clean` 也会清掉构建树。因此顺序是：

```
ci.py --only build,build_test  →  standardize.py --apply  →  standardize.py  →  ci.py
```

`run_all.sh` 已经用 `--no-clean-after` 处理了这件事。手工跑时若顺序反了，
工具会明确说"编译数据库不可用……先按 BUILD_COMMAND 构建一次"并自己构建
（配了 `BUILD_COMMAND` 的话）。

**验证日期**：2026-10。**复现命令**：删掉整个 `build/` 后直接跑
`python3 cxx_ci/standardize/standardize.py --config config/standardize.py`。

## 三、预期解决后的效果

### 3.1 目标流程（解决 2.3 之后）

```bash
# 新工程接入：拷工具、写配置、跑一次
cp -r cxx_ci /path/to/project/ && cd /path/to/project
$EDITOR config/ci.py          # 只填 ROOT 与 BUILD_TOOL 就能跑
$EDITOR config/standardize.py # 填两个 clang 配置路径与 TIDY_HEADER_FILTER

python3 cxx_ci/ci/ci.py                          # 门禁：直接绿
cxx-standardize --config config/standardize.py style --apply   # 一次修完
cxx-standardize --config config/standardize.py style           # 复查：绿
```

**"一次修完"的含义**：排版、风格、命名三类违规全部自动修掉，不需要人工介入，也不需要
理解 clang-tidy 的哪些检查有 fix-it、哪些没有。修完的代码仍然能编译（每一轮都有构建
验证兜底），且符合工程既有的排版约定（注释与手工列对齐不被破坏）。

### 3.2 可度量的验收标准

| 指标 | 现在 | 解决后 |
| --- | --- | --- |
| 三个工程风格诊断剩余 | 55 / 490 / 67 | **0 / 0 / 0** |
| 需要人工改的命名违规 | 49 / 485 / 67 | **0** |
| `--apply` 后的构建状态 | 绿（回退后保持原样） | 绿（改动生效） |
| 门禁首次接入到变绿 | 需要人工登记基线 | 一条命令 |
| 三个工程 `ci` 六阶段 | 全绿 | 全绿（不回退） |

### 3.3 对使用者的实际价值

1. **接入成本从"几天"降到"几分钟"**：现在接手一个存量工程，要么手工改上千处命名，
   要么逐条写 xfail 清单；解决后是一条命令。
2. **门禁重新有意义**：绿是常态、红一定指向新引入的问题。这是"工具值不值得用"的
   分水岭。
3. **规范可以被真正执行**：命名规范现在只能靠评审盯（规范里记着一次 SVN 回流把
   `s_` 静默改回 `g_`、一个月没人发现），解决后机器能守住。
4. **能力可迁移**：三个工程用的是同一套规范与同一套工具，第四个工程接进来只要写配置。

### 3.4 解决路径（三选一或组合）

| 方案 | 做法 | 代价 | 效果 |
| --- | --- | --- | --- |
| A. 自研改名引擎 | 用 clang-tidy 的诊断定位符号与目标名，自己按翻译单元解析角色、做整词替换 | 一块独立工作（本轮已摸清所有坑，含"角色不唯一就不猜"的判定） | 命名全自动，不依赖外部工具 |
| B. 装 `clang-rename` | 用 LLVM 官方符号改名工具做符号感知改名 | 需要一个额外的 clang 组件（本机未装，LLVM 18 起已移除） | 命名全自动，最稳 |
| C. 应用 + 登记基线 | `--apply` 修完能修的，剩下的一键写进 `xfail` | 最小 | 门禁立刻变绿可用，命名逐步人工清理 |

建议 **C 先做**（让工具当天就有用），**A 或 B 并行**（解决根本问题）。只做 C 的话，
命名规范仍然靠人工，与"机器守规则"的目标还差一步。

## 四、一句话总结

门禁（`ci`）扎实可用，三个真实工程全绿；自动修复的三件事——**排版、风格、命名**
——都能一次跑完（`standardize.py --apply`，缺省动作 `all`），剩下的只有 clang-tidy
本身不提供修复块的检查，走基线冻结。

## 五、已验环境与复现入口（2026-10）

| 项 | 值 |
| --- | --- |
| 解释器（standardize） | 3.11+，已实跑 **3.14.4**；`run_tests.sh` 会跑 3.11–3.14 矩阵 |
| 解释器（ci） | 3.4+，已在 CentOS 6.10 / Python 3.4.10 上跑通 |
| clang | 17.0.6；可用 `CLANG_FORMAT_BIN` / `CLANG_TIDY_BIN` 钉死来源 |
| 一次修完 | `python3 cxx_ci/standardize/standardize.py --config <工程>/config/standardize.py --apply` |
| 只看不改（门禁） | 同上去掉 `--apply`（或 `cxx_ci/run_all.sh`） |
| 存量违规冻结 | `cxx-standardize --config <工程>/config/standardize.py style --record` |

门禁（`ci`）已经扎实可用，三个真实工程全绿；自动修复的**非命名部分**已经跑通，
**命名部分**卡在 clang-tidy 的修复能力边界上——它的改名既不完整、又只覆盖单个
翻译单元、还会对"去前缀"类违规产出垃圾。把这一块补上（自研改名引擎或引入
`clang-rename`），并给"应用 + 登记基线"一条命令，工具就能达到预期的形态：
**接进来跑一次，绿；以后红，一定是新问题。**
