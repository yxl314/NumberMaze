# cxx_ci 改进提案（第二轮：吸收仓内 CI 门禁的独有功能）

日期：2026-10-12
读者假设：**未见过仓内 `CI/`**。因此本篇对每个缺口都完整描述 `CI/` 现在的做法
（机制、算法、配置、教训动机）、吸收后的预期效果、以及在 cxx_ci 的具体落地方案。
本篇实施完毕后，cxx_ci 应可完全退役 `CI/`（含第九节的配置迁移）。

设计前提（已确认，非缺陷）：双 Python 要求是环境分层的正确表达——老机器连
clang-14 都装不上，风格类功能对其本不存在，standardize 侧 py3.11 + pipx 不构成
部署短板；"一刀切 py3.4 可测"才是 `CI/` 时代被扭曲的旧约束。

## 一、总览：`CI/` 十步流水线 → cxx_ci 对应

| # | `CI/` 步骤 | 做什么 | cxx_ci 现状 |
|---|---|---|---|
| 1 | 配置审计 audit.py | 配置与代码/仓库 AST 比对 | **缺** → §二 |
| 2 | 边界检查 boundary.py | detail:: 归属 + 头文件宏守卫 | **缺** → §三 |
| 3 | 排版修复 format.py --fix | clang-format + 注释保护 | 已覆盖（standardize format 更强） |
| 4 | 清理 clean.py | 删构建产物 | 已覆盖（且保留编译数据库与日志） |
| 5 | 构建准备 prepare.py | 只生成 Makefile+moc 不编译 | 已覆盖（standardize TIDY_PREPARE） |
| 6 | 风格修复 tidy.py --fix | clang-tidy 自动修 | 已覆盖（export-fixes+回退，更强） |
| 7 | 编译 build.py | qmake+make | 已覆盖（cmake/qmake/qmake6） |
| 8 | 测试 test.py | 跑测试+xfail 清单 | 已覆盖（5 适配器+到期日 xfail，更强） |

## 二、P0 缺口 1：配置审计（源：`CI/Scripts/audit.py`）

### `CI/` 的做法

动机：门禁脚本自身也是最容易被绕过的代码。有人图省事在脚本里硬编码路径/工具名，
config 就会慢慢变成"摆设"——改 config 不生效，门禁行为随文件漂移。`CI/` 用三步
AST 审计把"代码必须严格经 config 取值"变成可机检的纪律：

1. **死配置**：枚举 config 全部公开键（值展开为字符串集合，含容器/字典元素），
   若某键名在所有被审计 py 文件中从未以 `cfg.<键>` 形式出现 → 报 `死配置: cfg.K
   从未被引用`。防止"改了没人用的配置还以为生效"。
2. **配置旁路字面量**：对被审计文件建 AST，收集所有字符串/字节常量（**排除
   docstring**——模块/函数/类体首表达式的常量不算），若某字面量与某个 config 键的
   值完全相等 → 报 `配置旁路: 文件:行 的字面量 'X' 应改用 cfg.K`。防止有人绕过
   config 直接写死同样的值（改 config 时那处不会跟着变）。
3. **编译标准锁定**：仓库根递归扫全部 `.pro`（冻结库的构建文件同样纳入——只锁
   标准不涉其代码；第三方目录跳过），要求承载变量
   （`QMAKE_CXXFLAGS_CXX11`/`QMAKE_CXXFLAGS_GNUCXX11`，按编译器 mkspec 二选一）
   必须存在且值为 `QMAKE_CXXFLAGS_*=−std=gnu++0x` 形式，任何一行出现其它
   `-std=`（**含注释里的示例**）即判红。动机是真实事故：`.pro` 注释里写的
   `-std=c++11` 示例曾被 qmake 静默当真，覆盖全局标准。

退出码 0=干净 1=有问题；每次输出 `[audit] 问题 N 处`。

### 预期效果

- 删掉任一 config 键的引用 → 门禁红，指到键名。
- 任何脚本硬编码与 config 值相同的字面量 → 门禁红，指到文件:行。
- 任一 `.pro`（含冻结库）漏锁或冲突 `-std=` → 门禁红。
- 双门禁并存期间，`CI/` 的 audit 直接退役，由 cxx_ci 自己审计自己。

### 落地方案

- `ci/`：新增 `lib/audit.py`，`ci.py` 启动时（config 加载成功后）自动执行，
  审计对象 = `ci/lib`+`ci/stages`+**项目 config 文件与项目测试脚本**；审计范围
  清单进 config（`AUDIT_FILES_GLOBS`）。stdlib `ast`，py3.4 兼容（`CI/` 已示范
  全部可用 3.4 语法写）。错误码新增类型 `1`（用法/配置）下 `AUDIT_DEAD_KEY`、
  `AUDIT_BYPASS_LITERAL`、`AUDIT_STD_DRIFT`。`--no-audit` 可跳（仅调试用）。
- `standardize/`：同款审计自己（3.11 下可写得漂亮些，逻辑同构）。
- 检查 3 的"承载变量/锁定值"进 config（`STD_PIN`、`STD_VARS`），cmake 项目对应
  `CMAKE_CXX_STANDARD` 锁定检查——按 BUILD_TOOL 分派。

## 三、P0 缺口 2：内部面边界检查（源：`CI/Scripts/boundary.py`）

注意：本检查管的是**仓内代码的内部面纪律**，与 §四"禁改区写保护"是两回事，两者
都要有。

### `CI/` 的做法

检查 1 —— **detail:: 归属**（只读，无自动修复）：
- config 声明 `DETAIL_DIRS`（允许出现 `detail::` 的目录 = 各模块自身目录，如
  `Tools/Logger`、`Tools/Notify`）与指纹 `DETAIL_MARK = "detail::"`。
- 对受管目录（SERVED）下全部源文件：位于 DETAIL_DIRS 内的跳过；否则先做**注释
  剥除**——逐字符状态机，正确跳过 `//`、`/* */`（跨行）、`"..."`/`'...'`（含转义），
  把注释位置替换成等长空格保持行列对齐——然后在剥除结果上搜 `detail::`。
- 命中 → 报文件/行号/行内容，判红。**故意不提供 --fix**：出现 detail:: 越界意味着
  有人绕过门面直接调内部实现，只能人工改回公开入口（如 `Notify::`、
  `capture_trace()`）。注释里提及 `detail::` 不误报（剥除保证）。

检查 2 —— **头文件宏守卫命名**（可 --fix）：
- 期望守卫名算法：文件相对仓库根路径（仓外文件用绝对路径）→ 非字母数字字符全部
  换 `_` → 全大写。例：`Source/CDBurn/Tools/Notify/Notify.h` →
  `SOURCE_CDBURN_TOOLS_NOTIFY_NOTIFY_H`。路径即身份，天然唯一、移动文件即强制改名。
- 取实际守卫：首个 `#ifndef X` 且其后有配对 `#define X` 才算；有 ifndef 无配对
  define 标记为残缺（`X?`）。
- `--fix`：缺失时在"文首空行与注释块之后"插入 `#ifndef/#define`（插入点由同款
  跳过注释的扫描器给出）并在文末补 `#endif // 守卫名`；名字不符的原地三处同步改名
  （#ifndef/#define/#endif 注释）。
- 退出码 0/1。

### 预期效果

- 新模块里 `using namespace Xxx::detail;` 写到模块外 → 红。
- 注释里写"内部实现见 detail::xxx" → 不报。
- 新头文件忘加守卫或守卫名随手起 → check 红且指到期望名；--fix 一次成型。

### 落地方案

- `ci/`：新增阶段 `boundary`（只读检查），置于 `clean` 之前——纪律违规没必要再花
  构建时间。`--fix` 语义跟随 `CI/`：仅修守卫，detail:: 不修。
- config 新增：`BOUNDARY_DIRS`（受管源目录）、`DETAIL_DIRS`、`DETAIL_MARK`、
  `GUARD_EXTS`。守卫名算法需要"仓库根"，用既有 `ROOT`。
- 算法可从 `CI/Scripts/boundary.py` 近乎原样移植（约 150 行，纯 stdlib re，
  py3.4 兼容）；`strip_comments` 状态机连同其转义处理一起搬，配单测：字符串内含
  `/*`、跨行注释中的 detail::、带守卫但缺 #define 等用例。
- 宏守卫与 clang-format/clang-tidy 的交互：standardize 的 format 会保持守卫与
  `#endif` 注释（clang-format IncludeGuard 相关行为），boundary 阶段在前、
  standardize check 在后（run_all.sh 既有顺序），无竞态。

## 四、P1 缺口 3：冻结库写保护（源：`CI/Scripts/ci_common.py` + `tidy.py`）

### `CI/` 的做法

背景：仓库里有**禁改区**——vendored 冻结库（本仓为 `FROZEN = ("TrLibBurnForLinux",
"UIController")`，第三方 `EXCLUDE = ("libisoburn",)` 连扫描都不进）。冻结库的教训
（写进 `CI/` 注释的原文逻辑）：**"诊断可见即可修"——一旦某个 TU 把冻结库头文件带
进 clang-tidy 诊断，自动修复工具会把改名/排版直接写进冻结库**，而那里的风格是库方
既定事实、项目不可改，改了就是越权破坏与上游同步能力。

`CI/` 的三件套防线（全部作用于 `--fix` 路径）：
1. **ensure_editable**：修复/清理的每个目标文件，路径任何一段命中 FROZEN → 直接
   终止 `冻结库严禁改动: <文件>`。
2. **frozen_snapshot**：修复动作前，对 FROZEN 下全部代码文件取 `mtime_ns` 快照。
3. **verify_frozen_untouched**：修复动作后复查，任何快照项 mtime 变化 →
   `冻结库被 --fix 写出(诊断泄漏): <清单>` 立即终止。防的是"目标在界内、但 fix-it
   落点穿透到界外头文件"的间接写入——单靠目标检查拦不住。

### cxx_ci 现状与差距

standardize 有 `SCOPE/WHITELIST/BLACKLIST`，但语义是"**不分析**黑名单文件"。缺的
正是第 2、3 道：`--apply` 走 clang-apply-replacements 时，替换块来自 TU 诊断，落点
可能位于黑名单/禁改区头文件；现行流程会照写不误（黑名单只管"分析谁"，不管"写到
哪"）。

### 预期效果

- 构造一条 fix-it 其落点在禁改区（例如冻结库头文件里可修的风格问题被本仓 TU 带
  出）→ `--apply` 整体拒绝、工作区字节级不变、错误码指名被触碰文件。
- 修复流程结束后禁改区 mtime 快照比对通过，否则回退并判红。

### 落地方案

- `standardize/config.py` 新增 `FROZEN`（与 SCOPE 黑名单**分列**：黑名单=不必分析
  的宽容语义，FROZEN=绝不可写的红线语义，合并会丢掉红线）。
- `style.py --apply` 流程改三处：应用前 `ensure_editable(replacement 全部落点文件)`
  （不是只查命令行目标）；应用前取快照、应用后（VERIFY 通过与否都要）比对，变化 →
  整体回退 + 新错误码 `FROZEN_TOUCHED`。
- check（只读）模式不受影响。`ci/` 无需改动（它根本不碰源码，CONTRACT 已定）。

## 五、P1 缺口 4：header-filter 强制防逃逸（源：`CI/Scripts/tidy.py`）

### `CI/` 的做法

`CI/` 每次调 clang-tidy 都在**命令行**传 `--header-filter=<config 里的
TIDY_HEADER_FILTER>`，命令行优先级高于项目 `.clang-tidy` 的 `HeaderFilterRegex`，
等于强制覆盖。`.clang-tidy` 内的对应注释写明：仓内那个值"仅为独立运行 clang-tidy
时兜底，唯一事实源是 config，tidy.py 会以命令行强制覆盖（防本文件被改出逃逸）"。
防的两种逃逸：把 HeaderFilterRegex 放宽 → 冻结库/Qt 头噪音涌入且 --fix 可写它们
（与 §四是同一事故的两面）；收窄 → 本仓头文件诊断被静默藏掉。

cxx_ci 把 HeaderFilterRegex 完全交给项目 `.clang-tidy` 自觉，工具不核对不覆盖。

### 预期效果

- 有人把 `.clang-tidy` 的 `HeaderFilterRegex` 改成 `.*` 或空 → 门禁行为不变（a
  方案）或立刻报 `CONFIG_DRIFT`（b 方案），不存在静默放宽。

### 落地方案（二选一，推荐 a）

- a. standardize config 增 `TIDY_HEADER_FILTER`，tidy 命令行以
  `--extra-arg-before=--header-filter=...` 注入（与 clang-tidy 17 兼容：后出现的
  `--config-file` 不能覆盖显式命令行参数）。注意 `.clang-tidy` 的 `Checks:` 仍
  走 --config-file，两条通道各管各的，README 写明分工。
- b. 只做一致性校验：启动时解析 `.clang-tidy` 的 `HeaderFilterRegex` 与 config 值
  比对，不一致报 `CONFIG_DRIFT`。实现小，但运行时不设防。

## 六、P1 缺口 5：ASan+LSan 双通道内存检测（源：`CI/Scripts/memtest.py`）

### `CI/` 的做法

不用 valgrind（太慢），用 ASan+LSan，且因本机环境有常驻注入软件以 **ptrace 附着
全部进程**（LSan 收尾扫描遇 Qt GUI 事件循环会被打到 fatal——探针证实是环境冲突而
非被测代码泄漏），设计了**双通道**：

- **通道 A（内存错误检测，全量用例）**：影子构建目录（`build/tests_asan`，qmake
  传 `QMAKE_CXXFLAGS+=-fsanitize=address -fno-omit-frame-pointer` +
  `LIBS+=-fsanitize=address`，asan 库必须置 LIBS 尾部）编译测试工程；运行时
  `LD_PRELOAD=<g++ -print-file-name=libasan.so>` 强制前置（环境注入库会抢
  DT_NEEDED 首位，不 preload 则拦截器失效）、`ASAN_OPTIONS=detect_leaks=0`。
  UAF/越界/双释由拦截器在发生当场抓，不依赖 ptrace，环境鲁棒。
- **通道 B（泄漏扫描，仅无 GUI 逻辑用例）**：同一二进制加 `--no-gui` 参数跑，
  `detect_leaks=1` + `LSAN_OPTIONS=suppressions=<lsan.supp>`（Qt 对象树所有权
  产生的存量"泄漏"以显式清单抑制，**清单必须存在否则终止**）。绕开 GUI 事件循环
  与 ptrace 注入的冲突面。
- **与 xfail 的集成规则（重要，别丢）**：判"失败是否全部为已知预期失败"时，输出中
  只要出现内存类指纹（`ERROR: AddressSanitizer`/`LeakSanitizer`/`Direct leak`…）
  **一律不算 xfail 豁免**——业务用例可以带病登记，内存错误永远不可；且 FAIL! 用例
  集合必须是清单的子集，漏登记一个即判负。

### 与 cxx_ci 现有 valgrind 路线的关系

互补而非替换：valgrind 归因（外部库自动识别、多次取交集、签名 xfail）适合合入门禁
的深度扫描；ASan 快一个数量级，适合日常。cxx_ci 已有 `STEPS_DEFAULT` 机制可以表达
"日常 asan / 合入 valgrind"，不需要新机制。

### 预期效果

- `MEMCHECK_TOOL=asan` 时：不编译主产物、注入一次堆越界秒级判红；泄漏只认无 GUI
  通道（防环境软件假 fatal）；业务 xfail 用例可豁免但内存指纹永不豁免。
- `MEMCHECK_TOOL=valgrind` 时行为与现在一致。

### 落地方案

- `ci/stages/memcheck.py` 按 `MEMCHECK_TOOL` 分派：`valgrind` 走现有路径；`asan`
  走新增 `lib/asan.py`——吸收上面四要点：影子构建目录、`LD_PRELOAD` 前置、双通道
  命令模板（GUI 通道禁泄漏、`--no-gui` 通道开泄漏 + supp 文件必须存在）、
  **内存指纹行优先级高于 xfail** 的判定函数。通道参数（额外测试二进制参数、
  supp 清单、内存指纹清单 `MEM_ERROR_MARKS`）全部进 config。
- qmake 之外的 cmake 项目：`-DCMAKE_CXX_FLAGS/EXE_LINKER_FLAGS` 等价注入，或提示
  asan 路线需构建侧预置（文档写明，不强求两工具全等）。
- py3.4 约束照常。

## 七、已覆盖且更强（备忘，不建设）

| 能力 | cxx_ci 优势 |
| --- | --- |
| 风格修复安全 | export-fixes + clang-apply-replacements + 逐文件 VERIFY + 失败整体回退（`CI/` 两段式并行 fix 无逐文件回退） |
| 内存判定（valgrind） | XML 归因 + AUTO_IGNORE_ROOTS + REPEAT 取交集 + 签名 xfail |
| xfail | 到期日 `@YYYY-MM-DD` + `XFAIL_STRICT` 防腐化 |
| 排版 | 注释保护三模式、幂等自检拒写、基线指纹漂移检测 |
| 工程性 | 协议行判定、16 位错误码、SKIPPED≠通过、阶段超时、增量取集、产物全量落盘 |
| 执行顺序 | run_all.sh 先 ci（行为）后 standardize（风格）＝ `CI/` "风格门禁殿后防遮蔽" |

## 八、明确不吸收

- **`--fix-naming` AST 改名专项**：`CI/` 自研它源于旧 clang-tidy（identifier-naming
  在 --fix 下无条件硬改名、无逐文件回退）。cxx_ci 的逐文件应用+回退已覆盖该风险，
  且前缀策略（如"局部变量去 v_"）clang-tidy 规则本身可表达（前缀置空）。
- **两段式并行 fix**：并行写源码竞态已被"逐文件应用+回退"更安全地解决。
- **手写 supp 升级为一等公民**：valgrind 侧归因已优于 supp；supp 保持可选精修。

## 九、配置迁移清单（退役 `CI/` 的前置，缺此则覆盖停在纸面）

把 `CI/Scripts/config.py` 中承载的本仓事实迁入 cxx_ci 项目配置：

| `CI/` 项 | 去向 |
| --- | --- |
| QMAKE/MAKE/主工程与测试 .pro 路径/构建目录 | ci/config（BUILD_* / TEST_* 系列） |
| TEST_ENV（QT_QPA_PLATFORM=offscreen）、TEST_WORKDIR | ci/config |
| TEST_PRO 的 `--no-gui` 约定、MEM_BUILD、MEM_ERROR_MARKS、lsan.supp | ci/config（§六新增项） |
| FROZEN / EXCLUDE | standardize/config（§四）与 ci/config（boundary 阶段跳过冻结库） |
| DETAIL_DIRS / DETAIL_MARK / GUARD_EXTS | ci/config（§三） |
| STD_PIN / STD_VARS | ci/config（§二） |
| SCOPE（SERVED）/TIDY_HEADER_FILTER | standardize/config（§五）；诊断归因 SCOPE |
| xfail.txt → ci.xfail、valgrind supp → MEMCHECK_SUPPRESSIONS（可选） | 格式按 cxx_ci 语法重写（加到期日） |
| .clang-tidy/.clang-format | 不动（项目根，standardize 经 CLANG_*_CONFIG 直指） |

# 实战记录（三个真实工程）

把 TrCDBurnForLinux 的 `.clang-format`（121 行）与 `.clang-tidy`（303 行）逐字
装进三个工程，只按各仓调整 `HeaderFilterRegex`，再用 cxx_ci 跑一遍。

配置放在**工具目录之外**（`config/ci.py` 与 `config/standardize.py`）：
`cxx_ci/` 在这些工程里是子模块，配置写进去提交不到工程自己的版本库，重新拉一次
工具还会把它覆盖掉。`run_all.sh` 按约定读 `<工程>/config/`。

## 结果

| 工程 | 构建与测试 | ci | standardize 首次 | 一次 `--apply` 之后 | 剩余 |
| --- | --- | --- | --- | --- | --- |
| singleproc | cmake + ctest + valgrind | 全绿 | 103 条 | 自动修 26 条，2 个文件被判"修复会破坏构建"并回退 | 77 条，全是命名 |
| stacklog | cmake + ctest + valgrind | 全绿 | 746 条 | 自动修 21 个文件、230 条，构建仍通过 | 506 条：命名 + 3 条没有 fix-it |
| qtproj | qmake + Qt 5.6 | 全绿 | 67 条 | 无可自动修项 | 67 条，全是命名 |

**"应用一次就全绿"只对了一半**：非命名类可以自动修完（stacklog 746 → 506，剩下的
全是命名），命名类按规范**必须人工**——规范自己写明了理由：clang-tidy 的
identifier-naming 没有 FixIt 开关，改名只落在被分析的那一个 TU 里，声明与定义分处
头文件与源文件时会把能编译的工程改成编译不过。因此三个工程的命名违规（77 / 506 /
67 条）都留待人工，这不是工具的缺陷，是规范定的边界。

## 实战暴露并修掉的问题

1. **配置审计在 cmake 工程上必然假阳性**：承载变量检查要求每个构建文件都写
   `CMAKE_CXX_STANDARD`，而子目录继承顶层是常态；检查 2 又把工具自身算进范围，
   而工具必然含 `CMAKE_CXX_STANDARD` 这类与配置取值同形的 schema 词汇。
2. **契约版本成了项目的必填项**：它是工具的属性，项目不写就被判成"取自不同代"。
3. **fork 的程序让 valgrind 报告不再是合法 XML**：子进程继承的是写了一半的文件
   描述符，只写自己那段与一个 `</valgrindoutput>`，于是 1 个开标签、N 个闭标签。
4. **ci 清过构建目录后 standardize 拒绝编译数据库**：编排里 ci 跑完只留数据库
   （那是另一个项目的输入），同目录的 `CMakeCache.txt` 已经不在。
5. **自动修复必须有构建验证**：没有验证时 clang-apply-replacements 会把两处重叠的
   fix-it 叠在一起，实测写出 `static_cast<std::size_t>(1024 * )1024` 这种编译不过
   的文本。原来只是一行提醒，现在直接拒绝。
6. **风格修复必须关掉命名检查**：`--apply` 改为以 `--checks` 覆盖配置、追加
   `-readability-identifier-naming`；预览不受影响，命名照常报告。
7. **编排要保留构建树**：cmake 会把编译数据库导出到构建目录（清掉构建树也还在），
   qmake 没有这个能力，只能从 Makefile 现推一份，构建树没了就推不出来。
8. **boundary 的错误信息要能指路**：stacklog 的 `detail` 是整个 `src/`（门面在
   `include/`），按"detail 只在自己的子目录里"配会满屏误报 48 处，而当时的输出只
   说"越出模块目录"，不说该怎么配。

## 配置层面的经验

- `HeaderFilterRegex` 要写具体：`(include|src|tests)/.*` 会把
  `/opt/qt-5.6.3/include/...` 一起放进来，qtproj 上从 67 条涨到 5501 条。
  写成 `include/<工程名>/.*` 才对。
- `DETAIL_DIRS` 按工程的内部实现层实际范围配，不要照抄"模块子目录"的形状。
- qmake 工程要给测试单独配 `TEST_BUILD_DIR`：测试工程常按相对路径引用主构建的
  静态库，与主工程共用构建目录会解析到错的位置。
- Qt 5.6 + clang 17 的 `clang-diagnostic-enum-constexpr-conversion` 是已知误报，
  用 `CLANG_TIDY_EXTRA_ARGS` 屏蔽。

## 还没做

  本次只做了"风格修复关掉命名"这一半。
